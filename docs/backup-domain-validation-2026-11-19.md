# 备份 WAL 遗漏与旧迁移夹具修复

2026-11-19 公开版本的 15 个失败用例已全部定向复验通过。本阶段 211 个不同用例的最新结果全部通过，覆盖备份、恢复、四组探索状态和六组旧迁移；没有重新运行完整 3,203 项集合，也没有新增原生游玩或 Windows 程序验收。

## 备份故障的实物依据

四项原有恢复检查在当前源码再次复现 `DID NOT RAISE ValueError`。隔离脚本发现 `Database.backup` 生成的文件沿用源库的 WAL 日志模式。编辑器保持连接时，已提交的变更位于同名 `-wal` 中，主文件大小和 SHA-256 仍可与索引吻合。恢复使用 `shutil.copyfile` 只复制主文件，于是候选验证看到的是更早的数据。

实测备份连接读取余额 666，原主文件 SHA-256 仍与索引相同，4,152 字节 WAL 存在，复制后的 SQLite 文件却读取余额 1000。该复现使用项目自有合成数据，证据保存在 `.cache/backup-domain-validation-20261119/wal-reproduction.json`；原四项失败在 `baseline.xml` 中保留。

`Database.backup` 现在在新生成的临时备份上完成 `journal_mode=DELETE`，关闭连接后发布独立文件。现用数据库继续使用 WAL，不改变原库的版本或运行方式。恢复及备份列表拒绝非空的 WAL、回滚日志和同名日志符号链接；复制后再次检查源快照日志，以捕获复制期间出现的新提交。没有挂起日志的旧 WAL 格式备份仍可恢复。

## 旧迁移夹具

其余 11 项失败涉及 0025、0028、0029、0030、0031、0032 的模拟旧库。夹具从当前 0037 构造旧结构时，遗漏移除 `rlv2_battle_loot_plans`，同时仍断言当前库只有 77 张表。

现先确认该未来表为空，再从模拟旧库删除；旧表数保持 71 或 74，迁移后的当前结构明确为 78 张表，新奖励方案表必须为空。原有字段、约束、行数据和用户同步结果仍逐项比较。受控中断后必须保持完整旧库，不能通过放宽旧表数量或忽略旧数据差异来通过检查。本阶段未修改产品数据库迁移逻辑。

## 验证及保留的失败

- 四项原始故障先复现失败。修复后的备份、保留策略和四组探索检查有 137 通过、1 失败；该失败是篡改地图夹具只更新哈希、没有更新实际文件大小，被更早的大小检查拒绝。补齐故意有效的索引大小后，该用例通过。两次结果均保留，138 个不同用例的最新结果通过。
- 新增三种恢复入口在复制期间出现 WAL 的检查，3 项通过。在线恢复、原位恢复及恢复到新文件均须在替换现用库前拒绝，原状态、原备份和恢复前快照规则有实际核对。
- 六组旧迁移共 70 项。首轮 66 通过、4 失败，原因是比较集合仍含刚迁移新增的空奖励方案表。改为逐项比较全部原表，同时单独断言新增表为空，四项复验通过。中断回滚和原用户结果保全通过。
- 以上合计 211 个不同用例，逐项最新结果全部通过；新增 11 个备份用例包含正常独立文件、未归档 WAL、回滚日志、旧格式兼容和复制期间提交。Ruff 及 `git diff --check` 通过。原发布 3,203 项结果保留，不能改写为本次全量通过。
