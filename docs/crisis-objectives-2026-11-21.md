# 危机合约 V2：任务进度事务组件

在[开战会话](crisis-battle-sessions-2026-11-20.md)和[结算输入绑定](crisis-finish-logs-2026-11-20.md)上新增指标集/宝藏条件及进度写入组件。它是最终结算事务的参与者，当前没有原生路由调用；结果分类、分数纪录、评论、领取奖励和最终回执仍需完成。未重建 EXE，不标记整套玩法完成。

## 实现与规则来源

`CrisisV2ObjectiveRules` 以已绑定地图的完整指纹核对来源，复用既有的符文连接、互斥、默认槽位、六维计分和挑战条件。当前只接纳实际首季存在的 `HIGHEST_TOTAL_SCORE` 指标集类型；宝藏的 `requestBagIdList/requestBagCnt` 逐项验证唯一性、引用及整数范围。未认识的类型、缺少的任务和不匹配版本拒绝。

**明确的本地任务策略**：通关且本次实际携带的指标集达到其 current/target 条件时，记为待领取任务。客户端消费者和表字段给出算术及状态依据，没有恢复官方后端的领奖算法。原生算术的 `0/0` 为真并不证明能领奖；没有任何所选普通符文的完成组单列为 `unverifiedEmptyPacks`，此组件不把它标成待领取，也不授予货币。该边界不推广为所有版本、所有玩法的通用规则。

永久图进度写入：所选普通符文置 3，附加符文写入 exRunes；满足挑战和指标集置 1，已领取的 2 保持。宝藏进度采用历次**单场**达成数量的最大值，不能把不同战斗分别完成的指标集累计成“同一场全部携带”。未通关不改变地图。临时图遇到永久专用指标集/宝藏定义时明确拒绝；匹配首季四张实际临时图没有这些定义，已另行核对。

内部 `record` 先重新核对自有账号、0039 会话、地图/数据和登录绑定，再验证当前保存字段，最后参与调用方的同一个 SQLite 事务。只更新地图任务，不更改金币/库存、干员、普通关卡、六维纪录和评论；不结束 BattleSession，不释放已有战斗锁，不将 bool 参数当作已完成的原生通关分类。未来最终结算必须把结果、纪录、评论、终态和回执一起提交，不能单独暴露这个组件作为成功结算接口。
