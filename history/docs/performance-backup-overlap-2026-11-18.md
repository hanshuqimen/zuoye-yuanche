# 自动备份期间的接口延迟

自动任务验证日备份和周备份的 SHA-256 时，原先一直持有业务请求共用的锁。即使当天和当周都已经有备份，邮件列表、编队写入和全量同步也会等两份文件校验完毕。

改动将备份文件的创建、列出、暂存和轮换放到独立锁下。SQLite 的在线备份读取已经提交的 WAL 状态。真正替换活动库时，恢复仍按固定顺序取得两把锁，在同一个业务维护窗口内保存最新状态、激活候选或回滚。定期 SHA-256 校验、保留范围和磁盘文件格式继续适用。

以下是同一 Windows 主机上实际 HTTPS 往返的 P95，单位为毫秒。使用本地 CA 校验证书，复用连接。前后均从相同 SHA-256 的合成存档开始，含 429 个合成干员和一组 12 人编队。约 5.79 MiB 和 95.90 MiB 两档存档用独立填充表改变备份体积，接口返回的角色规模相同。每条路径稳定运行取 80 次样本，备份场景取 24 次，各自的请求提交都落在实际校验期间。

| 存档 | 接口 | 无校验，修改前 → 后 | 校验重叠，修改前 → 后 |
| --- | --- | ---: | ---: |
| 5.79 MiB | 邮件列表 | 2.900 → 2.829 | 10.095 → 3.293 |
| 5.79 MiB | 编队写入 | 33.462 → 28.997 | 39.038 → 35.014 |
| 5.79 MiB | 全量同步 | 26.451 → 22.636 | 28.882 → 23.500 |
| 95.90 MiB | 邮件列表 | 2.323 → 2.341 | 112.587 → 4.372 |
| 95.90 MiB | 编队写入 | 30.385 → 30.305 | 153.097 → 49.670 |
| 95.90 MiB | 全量同步 | 22.238 → 21.359 | 132.481 → 25.196 |

每轮仍完整哈希两份备份。大存档前后 SHA-256 阶段 P95 约 108–130 ms，接口不再等待它完成。编队在压力样本中刚低于 50 ms，余量有限。统一条件下 1,334 个网络请求均返回 200，增量应用结果、编队与完整快照一致。34 个相关检查通过。其中新增两项分别在暂停校验时完成同步及写入，以及在另一个事务尚未提交时取得完整的上一份已提交状态。

未加载数据的源码服务启动后工作集为 114.21 MB（基线 114.18 MB）。合成数据和 95.90 MiB 存档下，请求后工作集为 121.51 MB。另以通用加载器只读验证了既有的 19 表缓存，输入字节 69.71 MB，耗时 1.07 秒，加载完成工作集 245.76 MB、峰值 269.72 MB。19 表以指纹 `e915675d…ae29` 识别，客户端匹配标记仍为 false。加载器进程的数字仅覆盖读取和验证，发起前后逐表 SHA-256 相同。

本次测量覆盖源码 HTTPS、有限的合成接口负载和本地加载器。局域网、完整长时游玩、实际原生客户端和新 Windows 发行物未验收。合成文件、存档、证书、日志和原始样本都留在本地 D 盘。证据在 `.cache/service-performance-20261118`，包含六组 `measurement.json`、`loader-measurement.json`、`checks-candidate.xml`、`candidate-source.json` 和复现脚本 `bench.py`。
