## 代理入口与实际失败

0-1已有三星且 saveBattleReplay 下发 `dungeon.stages.main_00-01.hasBattleReplay:true`，入口仍隐藏。复用冻结索引，补采12KB只读文件映射代码并解析静态 literal 链，确认：

- StageViewModel 隐藏值来自 `!StageData.canBattleReplay`。
- 选关模型再合并全局 `CheckIfUnlocked(AUTO_BATTLE=9)`；全局未解锁时 toggle 和 locked 两个控件都会隐藏。
- 目标9通过 holder `0xc0e7f58` → referent `0xc61dc58` → usage `0xa0010c81` → metadata literal34368，解析为内部关卡 `tr_06`；要求该可用玩家关卡 state>1。
- 已解锁但没有记录时影响可用资格，不能将“隐藏入口”直接解释成读取接口失败。客户端还缓存选关和全局解锁状态，需要重建页面或冷启动验证。

因此另建 replay-oct15-v3 副本，仅预置 tr_06 二星前置记录，不发奖励，未改动 v2。准备后54张表与 v2 比较，除该新增行外完全相同。它是UI合同夹具，不能证明玩家已真实打过 tr_06，也不能证明自然推进的完整教学闭环。

冷启动后原生代理勾选入口出现。原生 getBattleReplay 200，16.96ms，正确加载原四人固定代理编队。实际开始请求确认 squadId:"0"、name:null、12格编队、isReplay:1；无技能槽的 skillIndex 仍省略。旧 `6da1f64` 把可空名称当字符串，返回422，原生断线提示已保留。未扣理智、未创建新战斗。

该轮31次请求中30次200、1次上述422，无未知路由；正常停服后187项输入、48张其他账号表保持，数据库及外键通过，无活动战斗。证据位于 `.cache/replay-native-2026-10-15-v3`，详细静态报告位于 `.cache/rea-2026-10-15/replay-ui-unlock-followup-v2/REPORT.md`，各页、指针和 literal 均有范围及SHA收据。

## 代理事务实现

允许原生明确发送的 name:null，保留其他严格请求字段和模式限制。isReplay 开始改走独立代理阵容服务，核对匹配版本、三星来源战斗、账号归属、解锁前置、12格成员顺序和技能选择，随后复用普通理智预扣及战斗事务。保存代理日志时也核对其成员和技能确实来自该成功战斗，防止保存无法用于该战斗的记录后亮起代理标记。

普通保存编队可以修改或清空，旧记录仍从自身阵容启动；当前等级、养成和皮肤不要求等于旧日志。服务器保存代理来源指纹和原战斗关联，掉落随机状态保持独立，未把 journal 整数 randomSeed 当作服务器掉落种子。读取、开始和保存不会凭回放直接发奖，奖励仍只由战斗结算事务提交。

112项专项检查、945项完整检查（201.86秒）及Ruff通过，只有一项既有弃用警告。覆盖可空名称、独立编队、养成变动、无技能编码、归属、损坏日志、技能/阵容冲突、并发和重试、扣理智回滚、重复结算及重启。所有样本均为合成数据，未提交官方回放载荷或账号标识。
